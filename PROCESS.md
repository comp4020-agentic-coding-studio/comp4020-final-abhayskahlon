# Process

## From concept to working application

COMMONS began with the brief's focus on shared responsibility and social interaction. I explored whether caring for a virtual creature could give people a reason to interact and contribute together. Rather than build an individual pet simulator, I designed one creature shared by a group, with each person's care actions affecting its condition for everyone. This made collective responsibility the central interaction rather than competition between users.

I initially kept the implementation small: connecting the creature's state to persistent storage and making one care action work end to end. The concept and initial decisions are recorded in [92b29b2](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/92b29b2), followed by the stack setup and first working implementation ([e155a30](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/e155a30); [c8f9c94](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/c8f9c94)).

## Technology and architectural decisions

I used Astro, TypeScript, Drizzle ORM and SQLite. Astro suited the server-rendered interface, TypeScript supported consistency across the application, and Drizzle provided typed database queries. SQLite kept development and deployment simple, although the single-machine setup limits horizontal scaling.

I chose Server-Sent Events (SSE) over WebSockets because clients mainly need notifications when shared state changes; actions already use ordinary HTTP requests. A bidirectional protocol would add complexity without much benefit. After a transaction commits, the server broadcasts an event and clients fetch the latest state. This keeps the server authoritative, although it adds a request after an update. The alternatives and limitations are recorded in [ADR 0001](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/blob/main/docs/adr/0001-concurrent-care-and-realtime-sync.md).

I later introduced dedicated rooms, each with its own creature and care history. Cookie-based session identity avoided mandatory account registration, while the server derived room access from the session rather than trusting a client-supplied room identifier. This reduced joining friction but did not provide persistent account identity. The trade-offs are documented in [ADR 0002](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/blob/main/docs/adr/0002-multi-room-identity-and-access-control.md). Implementing rooms required coordinated changes to the schema, state handling, SSE and interface ([1f1d02d](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/1f1d02d); [dcd567f](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/dcd567f)).

## Learning to work with agents

My experience with agents started before COMMONS. During Crit 2, I experimented with Claude-generated images but found that the SVG outputs had limitations for the visual result I wanted. I explored alternatives and used stock photographs instead. By Crit 4, I was experimenting with specialised subagents, dividing visual-design and sound/instrument-related work between agents so both areas could progress simultaneously rather than sequentially. I reviewed and integrated their outputs, learning both the potential of parallel work and the need to coordinate separate contributions.

My prompting strategy changed following feedback from my tutor, Ushvini, during Crit 9. We discussed the trade-offs between one large prompt and several smaller prompts, particularly their effects on token utilisation and response time. I adopted a two-stage approach: one larger initial prompt established the project skeleton and overall requirements; subsequent smaller prompts focused on implementing, checking, optimising and validating individual features. This provided context at the beginning while keeping later interactions targeted. Smaller prompts were not automatically better, since they could require repeated context and additional interactions.

Resource management became another lesson. I monitored my Claude balance in a separate window rather than using a budget plugin. I underestimated how quickly usage could accumulate and exhausted my balance before Crit 11, leaving me unable to use Claude during class. I learned to avoid unnecessary repeated prompts and reserve usage for important development and verification milestones.

## Development and debugging

My development practice changed across the weekly crits. [Crit 8](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/blob/main/reflections/crit-8.md) records the move towards a working single-room application. I initially relied heavily on scripted tests, but a human playtest exposed behaviour they had missed. I directed the agent to gather diagnostic evidence in a real browser rather than continue guessing at fixes.

By [Crit 9](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/blob/main/reflections/crit-9.md), I no longer treated passing tests as sufficient: I required the agent to render and inspect the actual page. During [Crit 10](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/blob/main/reflections/crit-10.md), the agent identified a conflict between new room-feature instructions and existing `CLAUDE.md` rules and asked me to resolve it before implementation. My workflow therefore developed from scripted checks, to browser verification, to checking project constraints before coding.

A form-handling bug demonstrated why browser verification mattered. A hidden input named `action` shadowed the browser's `form.action` property, causing a request to use an invalid URL. Scripted tests had not exposed it; a real browser interaction did. The fix used `form.getAttribute("action")` and added `spec/action-form-url.test.ts` as a regression guard ([a8d100c](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/a8d100c3e3e50c9f2175a6364048ca8f68eb5001)).

I incorporated the lesson into the agent harness. [Commit 9322e99](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/9322e99) added a standing `CLAUDE.md` rule against reading `form.action`, documented the safe alternative, and required `refreshLiveState()` after every action attempt, including rejected actions. It also clarified that HTML responses must not be presented as rejection reasons. The regression test has a limitation: jsdom does not reproduce the original property-shadowing behaviour, so it guards against reintroducing the known-bad pattern rather than reproducing the browser failure.

A separate issue left the Recent Care panel stale even though the database recorded the action. I traced the request, transaction, SSE notification and client refresh, then unified the live-state update path ([43016f5](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/43016f5a7d7fa59f3834389a51c8f4d8a4ec0ba2)). The sleep countdown exposed inconsistencies between tabs and inaccurate client clocks. An initial resynchronisation fix was followed by server-based timing and independently testable countdown logic ([20dcb15](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/20dcb15b5a456c300a41d46336d905ee914b4fe6); [c74f96c](https://github.com/comp4020-agentic-coding-studio/comp4020-final-abhayskahlon/commit/c74f96ccc4f43cbd62bf4b4659b36b4b7606663c)).

## Verification and reflection

The test inventory I checked contained 160 passing tests across 26 specification files. Coverage included core logic, concurrency, sessions, room isolation, persistence after server restart, real-time updates, progression, Adventure mechanics, logging and regression guards. The concurrency tests compare final-state results against valid sequential orderings. The persistence test starts a separate server process, restarts it and checks that state survives.

I also manually checked progressive enhancement with JavaScript disabled, keyboard navigation and focus visibility, selected colour-contrast pairs, desktop and mobile layouts, and two independent browser sessions sharing a room. These were manual checks, not automated accessibility or visual-regression tests. There was no automated accessibility test, slow or interrupted network conditions were not comprehensively tested, and the concurrency test excluded sleep from its concurrent-action matrix.

Building COMMONS changed how I approach agent-assisted development. Claude can produce substantial amounts of code, but its output requires continual validation. A specific prompt does not guarantee the result will match my intention. I learned to inspect the output, identify differences and refine the instructions rather than assume the first response was correct. In another project, I would establish constraints and verification practices earlier, manage agent usage more carefully, and leave more time for integration and browser testing.
